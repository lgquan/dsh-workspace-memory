# DSH-WM-20260830-01：错误记忆与后续纠正并存导致冲突召回

## 问题信息

- 发现日期：2026-08-30
- 相关模块：`src/core.ts`、`src/index.ts`、`src/client/index.tsx`
- 状态：已解决
- 验证情况：核心测试、运行时测试、TypeScript 类型检查、构建、打包检查、diff 检查和真实 DSH Web/Harness 对话验收均已通过

## 问题描述

旧实现只用词法 Dice 相似度识别近重复记忆。后续对话纠正错误事实时，如果新旧说法相似度低于 `0.68`，正确说法会作为新条目追加，错误条目继续保持有效；两条冲突记忆随后可能同时被召回。即使相似度达到阈值，旧实现也只在新正文不短于旧正文时替换内容，导致更短、更准确的纠正无法覆盖错误正文。

蒸馏器原先只看到当前 checkpoint 消息，不知道已有记忆及其 ID，因此不能明确表达“修订”“取代”或“冲突”。稳定摘要又只按固定 checkpoint 周期重建，workspace 记忆发生变更后，旧事实可能继续在后续 Agent step 中注入。

## 证据与复现

旧实现的关键行为：

- `applyProposals` 对所有非 deleted 条目计算词法 Dice，相似度低于 `0.68` 时新增。
- 近重复更新使用正文长度作为替换条件，长度不是事实正确性的代理。
- `DistillInput` 不包含已有记忆，蒸馏器只接收本次 staged messages。
- `searchEntries` 和摘要生成只排除 deleted，无法表达 superseded 或 conflict。
- workspace 摘要只在 `checkpointCount % consolidateEvery === 0` 或摘要为空时重建。

可复现场景：

1. 旧 checkpoint 把“项目使用 MySQL”保存为长期记忆。
2. 用户后续明确纠正“前面说错了，项目实际使用 PostgreSQL”。
3. 新旧措辞未通过近重复阈值，系统新增 PostgreSQL 条目。
4. recall 同时返回 MySQL 和 PostgreSQL，稳定摘要仍可能包含 MySQL。

## 影响

- Agent 可能依据过时事实回答，且无法知道两条记忆是否属于同一冲突。
- 调高新近度或降低旧记忆权重只能隐藏冲突，不能恢复事实一致性。
- 自动覆盖旧条目又可能静默删除正确记忆，因此纠错必须采用比普通去重更保守的证据门槛。
- 原地更新不保留旧正文，缺少审计和回滚依据。

## 原因判断

旧数据模型只有 `active | deleted`，没有事实版本和冲突关系；蒸馏输出只有无目标的 memory proposals，没有操作语义；应用层将“同义改写”“明确纠正”“疑似冲突”统一压缩成相似度去重问题。

## 解决方案

### 安全不变量

明确用户纠正才自动 supersede；疑似冲突显式标记 conflict；普通改写保存 revision；旧版本不静默消失。

### 状态和关系

`MemoryEntry.status` 扩展为：

- `active`：参与普通召回和稳定摘要。
- `conflict`：参与相关召回，但不进入稳定摘要。
- `superseded`：保留审计，不参与普通召回和稳定摘要。
- `deleted`：用户明确删除，不参与召回和摘要。

冲突组使用 `conflictGroupId`。同组可见成员的 `conflictWith` 在读取时动态计算，避免维护双向 ID 数组。单个明确纠正只取代指定目标成员，不能因命中一个成员而误伤同组其他成员；组级解决需要未来显式的组确认操作。取代链使用 `supersedes` 和 `supersededBy`；唯一 successor 可以重定向到当前链头，多 successor 分叉必须降级为 conflict。

普通 revise 和近重复更新在覆盖前将旧正文、标题、描述和时间写入 `revisions`。forget 仍允许删除 superseded 条目，只拒绝已经 deleted 的条目。

### 版本化操作契约

新版蒸馏输出为：

```json
{"version":1,"operations":[{"op":"add","scope":"workspace","content":"..."}]}
```

操作包括 `add`、`revise`、`supersede` 和 `flag-conflict`。旧的裸 `MemoryProposal[]` 及 `{"memories":[]}` 兼容为 add 操作。

每次 checkpoint 在调用蒸馏器前选择有限候选记忆：词法命中、topic/type/tag 命中及最近条目合并去重，默认最多 20 条、12 KB，同时包含当前 workspace 和 global 候选。

supersede 的机械验证要求：

- `targetId` 和 `targetScope` 能定位已有条目；
- `evidenceMessageIds` 至少包含本次 checkpoint 的一条 user 消息；
- `newQuote` 是该 user 消息的非空原文子串；
- `oldQuote` 是解析到当前链头后 `target.content` 的非空原文子串。

quote 只证明证据来源，不单独证明语义正确；confidence 不能单独授权 supersede。助手自行验证发现的差异在 v1 中只能 flag-conflict。revise 仍需通过近重复阈值，不能成为任意覆盖入口。

### Scope、锁和摘要

操作使用 `targetScope` 跨 scope 定位目标。workspace checkpoint 可以纠正 global 记忆，并触发 global 摘要重建。跨 scope mutation 固定沿用现有 `workspace -> global` 获取顺序，禁止新增反向嵌套路径。

状态过滤按用途分开：

- recall：`active | conflict`
- summary：`active`
- 去重候选：`active | conflict`
- forget：除 `deleted` 外均可定位

workspace 或 global 发生 add/revise/supersede/conflict 后立即重建受影响摘要。被拒绝操作及原因写入 checkpoint Markdown 审计。

## 处理记录

- 移除近重复更新的正文长度门槛。
- 增加 `revisions`、`conflictGroupId`、`supersedes`、`supersededBy` 和四态 status。
- 增加 recall、summary、dedup 三类状态谓词；保留 forget 的独立规则。
- 增加有限候选集和版本化 operation 兼容层。
- 增加 supersede 的 user quote/target quote 机械验证。
- 增加唯一 successor 重定向、分叉降级 conflict 和跨 scope mutation。
- mutation 后立即重建摘要；checkpoint 记录操作接受或拒绝原因。
- 设置页展示 active/conflict/superseded 状态及 revise 历史。
