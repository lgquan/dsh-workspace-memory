- 复现工作区：测试工作区，Session 共完成 2 个 turn

## 问题描述

记忆插件在 `agent/turn-stopping` 时读取 `agent.session.deriveMessages().slice(-80)`。当前实现会接收所有 role 为 `user` 的派生消息，只排除 `source.kind = workspace-memory`。

DSH 会把 Agent 指令、运行时上下文、Skill 目录和时间上下文也表示为 user role 消息。插件因此将这些运行时注入内容误认为真实用户对话，交给记忆整理模型，并用它们参与已有记忆候选检索。这既增加输入 token，也会让宽泛的系统说明命中更多历史记忆。

## 证据与复现

目标 Session 只有 2 次 turn 完成事件，记忆状态记录 2 次整理调用、0 次失败、0 次重试、0 reasoning token：

```text
inputTokens=5,017
cacheReadTokens=8,198
outputTokens=149
totalTokens=13,364
```

DSH 的 `TokenUsage` 契约说明各输入字段互斥：`inputTokens` 是未缓存输入，`cacheReadTokens` 是缓存读取，`totalTokens` 是包含聚合输入与输出的完整调用量。因此 13,364 不是插件重复相加，但其中 8,198 为缓存命中 token，不能直接等同于未缓存输入费用。

第一轮 Session 派生消息构成为：

```text
真实用户消息             10 字符
agent-instructions    7,435 字符
runtime-context       2,377 字符
skill-catalog         1,019 字符
time-context            262 字符
助手回复                208 字符
合计                 11,311 字符
```

第一轮 checkpoint 的 Conversation 实际为 11,395 字符。以同一批消息运行当前候选选择函数，在当时工作区和全局共 41 条记忆中选出 17 条，序列化大小约 11,742 bytes，接近现有 20 条/12,000 bytes 上限。第二轮真实用户与助手正文合计只有约 76 字符，`workspace-memory` 注入已被现有过滤排除。

对应 checkpoint 时间为 2026-11-14 20:53:42 和 20:56:13。两次调用均正常 `finish=stop`，没有截断、JSON 修复或后台重放。

## 影响

- 新 Session 首轮可能重复把稳定的 Agent 指令、运行时上下文和 Skill 目录发送给记忆模型。
- 注入内容通常远大于真实用户消息，导致短对话也显示较高整理 token。
- 宽泛注入内容会扩大历史记忆候选集合，使每次整理更接近 12 KB 旧记忆上限。
- 记忆数量增加时，候选上下文会增长到最多 20 条/12 KB，但不会随全部记忆无限增长；对话批次也受 40,000 字符上限约束。因此当前成本有上界，但上界明显偏高且包含不应整理的内容。
- `totalTokens` 展示的是模型上下文规模而不是实际货币费用；缓存读取通常有折扣，当前界面无法表达这种价格差异。

## 原因判断

`conversationMessages()` 只依据消息 role 判断是否属于对话。DSH 的派生消息模型中，role 为 user 并不等价于终端用户输入；还必须检查 `message.source.kind`。

## 解决方案

1. 明确真实对话来源白名单：只纳入实际用户输入和模型助手正文；排除 `agent-instructions`、`runtime-context`、`skill-catalog`、`time-context`、`workspace-memory` 及其他运行时注入来源。
2. 增加回归测试：同一 turn 同时包含真实用户消息和多类注入消息时，整理输入只能包含真实用户与助手正文。
3. 候选记忆检索只使用过滤后的真实对话文本，避免注入说明扩大匹配范围。
4. 修复后使用该 Session 的等价事件回放，比较整理消息字符数、候选条数和输入 token；预期第一轮从 11,311 字符降到约 218 字符，候选记忆也显著减少。
5. 另行评估是否在 token 悬停详情中区分未缓存输入、缓存读取和输出，避免把总上下文量误解为实际费用。
