# DSH-WM-20260830-04：语音委派子会话未纳入记忆整理

## 问题信息

- 发现日期：2026-08-30
- 发现会话：主会话 `session-92da8fc2-632f-433d-a666-eea78e7f52ff`；子会话 `session-3e62a88d-7553-47fb-816e-aa4de6f1d81d`、`session-93f2a8c4-be14-479a-8236-4e400ea3b7e9`
- 相关模块：`dsh-workspace-memory/src/index.ts`、`dsh-voco/packages/voice-assistant/src/index.ts`
- 状态：已解决
- 验证情况：代码实现、针对性语音测试、记忆运行时集成测试、两个仓库的 TypeScript 检查、全量测试、构建、发布包内容检查、NPM 发布及从 NPM 重装验证均已通过

## 问题描述

语音前台把委派任务放入独立的子 Agent Session。主语音 Session 与子 Session 都继承同一 `cwd`，也都注册到同一 workspace，因此具备写入同一 workspace memory scope 的基础条件。但是，当前记忆插件的通用 Agent checkpoint 明确跳过所有 `parentSession` 非空或 `origin === 'subagent'` 的 Session；语音插件的专用 checkpoint 又只读取主语音 Session 中已完成的 `voice/utterance-end` 事件。

结果是：主语音对话会进入记忆整理，委派子 Session 内的用户消息、助手最终答复及其确认到的项目事实不会进入记忆整理。主会话里如果存在完成态语音转述，转述本身可以进入；但它不等价于对子 Session 对话的完整提交，而且被中断的语音输出也会被过滤。

## 证据与复现

### Scope 归属

三个真实 Session 的 `cwd` 都是 `C:\Users\QUAN\Desktop\1`。两个子 Session 的 header 同时包含：

- `parentSession: session-92da8fc2-632f-433d-a666-eea78e7f52ff`
- `origin: subagent`
- `delegationDepth: 1`

该目录对应记忆 scope `ws-5340a345c965a337da67`。`WorkspaceMemoryService.resolveCwd()` 通过 Session header 或持久化 header 的 `cwd` 解析 scope，所以只要显式提交 checkpoint，主子 Session 会自然汇总到同一个 workspace scope。

### 通用 Agent checkpoint 排除子 Session

`dsh-workspace-memory/src/index.ts` 的 `installAgentCheckpointing()` 在 `agent/turn-stopping` 时执行：

```ts
if (agent.session.header.parentSession !== undefined || agent.session.header.origin === 'subagent') return
```

因此两个语音委派子 Session 都不会通过通用 Agent 路径提交。

### 语音专用 checkpoint 只读取主 Session

`dsh-voco/packages/voice-assistant/src/index.ts` 的 `submitVoiceMemory()` 调用 `requireSourceSession(binding)`，只从主语音 Session 读取 `voice/utterance-end` 且 `state === 'completed'` 的事件，并始终以 `binding.sessionId` 提交。调用点只有：

- `output_text.done` 时提交 `segment-end`
- `voice/session-closed` 时强制提交 `session-close`

当前 `WorkspaceMemoryLike` 契约也只声明 `segment-end | session-close`，Voco 没有委派任务完成后的 `task-end` 提交路径。

### 真实 checkpoint

主会话在 2026-08-30 22:22:21 生成：

`C:\Users\QUAN\.dsh\workspace-memory\scopes\ws-5340a345c965a337da67\checkpoints\2026-08-30T14-22-21.696Z.d9f3e5b2-8e2f-4f83-85f1-414f09aebca9.md`

该 checkpoint 只包含主会话的两条用户委派原话：

1. 读取工作区根目录并列出文件名。
2. 读取 `package.json` 第一行。

两个子 Session 中实际存在的工具读取结果和助手最终答复均未出现。例如子 Session 已确认根目录只有 `工作约定.md` 和 `empty.txt`，另一个子 Session 已确认根目录不存在 `package.json`；这些内容没有被提交给蒸馏器。

## 影响

- 语音委派任务发现的持久项目事实可能不会形成长期记忆。
- 一次语音会话创建多个子 Session 时，每个子 Session 都会被同样跳过。
- 后续 recall 能在子 Agent 中正常读取同一 workspace 的既有记忆，但子 Agent 产生的新事实不能反向沉淀，读写行为不对称。
- 仅依赖主会话的语音转述会丢失被中断输出，并可能压缩或遗漏后台结果，不能作为可靠替代。

## 原因判断

两个独立设计组合后形成了提交空档：

- 记忆插件为避免任意子 Agent 重复整理或引入后台噪声，通用 checkpoint 排除 subagent。
- Voco 为主语音对话实现了显式 checkpoint，但没有在委派任务终止时为其自有子 Session 实现对应提交。

Scope 解析和 workspace 注册本身兼容，不需要为主子会话建立新的聚合模型；缺失的是 Voco 所有权边界内的子 Session 触发器。

## 解决方案

保留记忆插件通用 hook 对任意 subagent 的排除，避免把所有后台 Agent 的中间过程无差别写入长期记忆。由 `voice-assistant` 对自己创建且 descriptor provider 为 `voice-assistant` 的子 Session 负责显式提交：

1. 委派任务成功完成时，从 Voco 的 `ActiveTask` 读取权威用户原始请求、已接受的补充要求和最终可见结果。
2. 不提交 runtime context、workspace memory、voice handoff、reasoning、工具调用日志和大段中间过程。
3. 调用 `workspaceMemory.checkpoint({ sessionId: taskSessionId, messages, reason: 'task-end' })`。由子 Session 自身的 `cwd` 解析到与主会话相同的 workspace scope。
4. 使用 task ID 派生稳定消息 ID，并由 memory engine 的 `seenMessageIds` 保证 continuous policy、多轮 followup 和重复 terminal 事件下幂等。
5. 失败、取消、中断和等待用户继续的任务不提交，不能把未完成推断当作稳定事实。
6. 扩展 Voco 的 `WorkspaceMemoryLike` reason 类型以接受 `task-end`，并增加主会话与多个子会话共享 scope 的集成测试。

不建议直接删除通用 subagent 排除条件。那会改变所有 DSH 子 Agent 的记忆语义，容易造成重复 checkpoint、注入内容被再次蒸馏及大量低价值后台过程进入候选池，影响范围超过本问题。
