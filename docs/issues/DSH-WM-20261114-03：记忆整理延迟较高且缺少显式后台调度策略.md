# DSH-WM-20261114-03：记忆整理延迟较高且缺少显式后台调度策略

## 问题信息

- 发现日期：2026-11-14
- 发现会话：Codex 会话 `01a1d968-d8ce-7a33-b881-8e10529087ef`
- 相关模块或代码：`src/index.ts`、`src/core.ts`、`test/runtime.spec.ts`、`test/core.spec.ts`
- 状态：已解决
- 验证情况：已实现 15 秒合并窗口、有界后台队列、启动恢复与状态展示；自动化并发测试、构建和隔离 profile 启动验证通过

## 问题描述

用户希望在 DSH 服务运行期间持续处理记忆任务，新对话轮次完成后尽快整理，避免设置页长期积累大量待整理消息。当前插件会及时把新消息写入持久化 pending，但默认不会在每个完成轮次后立刻调用模型，而是等待累计阈值或空闲超时。

“固定记忆模型”和“后台整理频率”是两个独立维度。固定模型只决定每次整理请求路由到哪个 provider/model，不会自动建立独立进程、提高调用频率或绕过共享 provider 的并发与限流。

## 证据与复现

- 主会话结束一个 Agent turn 时，`agent/turn-stopping` 会异步调用 `checkpoint()`，前台不等待整理完成。
- 新消息会立即写入持久化 `pendingMessages`。
- 默认真正触发模型整理的条件为任一满足：累计 `10` 条用户消息、累计 `4000` 字符、最后写入后空闲 `300000ms`（5 分钟）。
- 插件启动时会扫描已有 pending，并按剩余空闲时间恢复定时任务。
- 整理失败后会以 1 秒起步、最高 30 秒的指数退避自动重试；成功前 pending 不会删除。
- `inFlightMessages` 能防止同一 scope 的同一批消息被重复整理，但当前没有明确的全局后台队列或全局并发上限。多个工作区同时达到条件时，可以产生多个并发模型请求。

因此，现有实现已经具有“DSH 运行时后台处理、重启恢复、失败重试”的基本属性，但不满足“每个完成轮次后近实时整理”的延迟目标。

## 影响

- 默认 5 分钟空闲窗口会让少量但重要的新事实在一段时间内只存在于 pending，不能被后续 Session 立即召回。
- 设置页可能长期显示较多待整理消息，用户难以区分正常批处理等待和实际失败。
- 简单把阈值改为每条消息立即调用，可能显著增加模型调用次数、费用、限流概率和重复改写，并在多个工作区活跃时形成并发突发。
- 即使整理模型与前台会话选择不同，如果两者使用同一 provider、账号、网关或本地推理服务，仍可能共享速率和算力容量。

## 原因判断

当前策略优先降低模型调用次数，采用累计阈值和 5 分钟空闲批处理。用户现在更重视低延迟召回，现有默认值与期望不一致。

模型 API 请求彼此独立，不存在一个模型在对话和记忆之间“分心”的状态。固定不同模型能够稳定质量和成本；选择不同 provider 时还可能隔离部分配额，但它本身不解决调度、并发、失败或速率限制。

## 解决方案

1. 采用“完成轮次后的短暂合并窗口”，而不是每出现一条流式消息就调用模型。只在主 Agent turn 正常收尾后调度，等待约 15 至 30 秒合并同一 scope 的连续活动。
2. 普通 `agent/turn-stopping` 使用 deferred checkpoint：完整用户/助手轮次先持久化，不在前台调用模型，随后由 15 秒合并窗口触发；无需改变批处理调用方保留的 `checkpointTurns` 兼容配置。
3. 增加显式后台调度队列：同一 scope 同时最多一个整理任务；后续消息合并到下一批；全局并发默认 1，可配置为 1 至 2，避免多个工作区同时触发请求风暴。
4. 保留现有持久化 pending、启动恢复和指数退避；DSH 未运行时不承诺处理，服务重新启动后继续未完成任务。
5. 固定记忆模型只负责路由。若该路由不可用，任务保持 pending 并进入退避，不静默切换到前台会话模型。
6. 设置页增加后台状态：待整理数量、是否正在整理、上次成功时间、下次计划时间和最近错误，使“正常等待”与“故障堆积”可区分。
7. 保留可选的批处理模式供成本敏感用户使用；建议默认采用近实时的“每轮 + 短暂合并”模式，而不是无条件逐消息调用。
8. 增加测试覆盖：单轮触发、短窗口合并、同 scope 串行、跨 scope 全局并发上限、整理期间追加消息、重启恢复、失败退避，以及前台 turn 不等待后台整理。
