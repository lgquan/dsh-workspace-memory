## 问题描述

项目工作区长期有大量普通对话，但设置页持续显示 `21条`、`待整理: 58`、`整理次数: 7`。记忆条目已经存在，普通对话消息却没有继续被整理。需要区分两层问题：58 条消息在服务重启前已经形成，说明重启不是最初原因；重启后仍保持不动，则暴露了恢复触发器缺失问题。

## 证据与复现

### 工作区状态

从 scope 的 `state.json` 读取到：

- `checkpointCount`: `7`
- `pendingMessages`: `58`
- pending 消息中 user 消息 `6` 条、assistant 消息 `52` 条
- 待整理文本总长度约 `79,925` 字符
- `lastCheckpointAt`: `2026-09-02T08:16:12.725Z`
- `lastBufferedAt`: `2026-09-02T17:44:43.292Z`
- `seenMessageIds`: `26`

当前默认整理条件为：

- `checkpointTurns`: `10`
- `checkpointChars`: `4000`
- `idleCheckpointMs`: `300000`（5 分钟）
- `consolidateEvery`: `5`

待整理字符数已经远超 `checkpointChars`，因此不是“没有达到阈值”。此前已经成功生成 7 个 checkpoint 文件，说明阈值判断和基本整理路径曾经正常工作。

### 指定会话状态

从 `C:\Users\QUAN\.dsh\storages\session_projcache_archive_manager.json` 核实：

- 会话共 8 轮
- `openStep: null`
- `pendingCalls: {}`
- `plan.active: false`
- `plan.running: null`
- 最后一轮正常结束，最后一个 `turn/end` 的 `reason.kind` 为 `completed`
- 会话日志以 `session/end-seed` 收尾

因此该会话不是因为 Agent 任务仍在运行或 Todo 未完成而无法整理。

### 运行时实现证据

`src/index.ts` 中：

- `idleTimers` 是运行时实例上的内存 `Map`。
- 构造函数安装 hook、工具和服务清理逻辑，但没有读取现有 scope 的 `state.json` 并恢复 pending 的 idle timer。
- `checkpoint()` 只有在 `engine.checkpoint()` 返回后才调用 `updateIdleTimer()`。
- `updateIdleTimer()` 在当前进程内创建 5 分钟 `setTimeout`；当 `pending === 0` 或 checkpoint 失败时不会创建 timer。
- 服务重启会清空 `idleTimers`，而重启后如果没有新的 checkpoint 调用或新的缓冲事件，就不会再次调用 `updateIdleTimer()`。

`src/core.ts` 的 `checkpointEligible()` 已包含 idle 条件：只要存在 pending 消息且距 `lastBufferedAt` 超过 `idleCheckpointMs`，`idle` checkpoint 即可执行。因此引擎具备按持久化时间判断“应立即整理”的能力，缺失在启动恢复触发器。

## 影响

- 服务重启后，已有 pending 消息可能无限期停留，直到新的事件偶然再次调用 checkpoint 路径。
- 设置页的“待整理”数量会长期增长，用户会误以为记忆整理整体失效。
- 已落库的 21 条记忆与 58 条待整理消息是两个不同计数；前者不能证明后者已经完成整理。
- 如果进程在蒸馏尚未提交时退出，pending 会被保留，但本次蒸馏结果不会自动恢复，进一步放大该问题。

## 原因判断

已确认的行为缺口：pending buffer 是持久化的，但 idle checkpoint 的定时器是进程内状态，插件启动时没有为已有 pending scope 恢复定时器或主动触发一次 checkpoint。

结合时间线，首要故障发生在重启之前：最后一次成功 checkpoint 是 `16:16`，而 58 条消息在 `17:44` 的会话结束时已经进入 pending。此时 6 条 user 消息和约 79,925 个字符已经满足当前 `segment-end` 的字符阈值，理论上应进入蒸馏并提交。现有持久化状态没有记录这次调用是“未触发”还是“蒸馏失败”，但代码存在一个确定的放大缺口：checkpoint 返回 `failed` 时，`updateIdleTimer()` 不会建立重试定时器。因此一次模型路由、网络或宿主事件异常，就可能让 pending 在重启前后都长期停留。

尚未确认的具体触发点：重启前最后一次 `agent/turn-stopping` 是否完全没有到达插件，或到达后 `distill` 是否返回失败。当前只有运行时日志才能区分这两种情况，而 checkpoint 结果没有持久化错误记录。可以确定的是，重启恢复缺失和失败不重试共同构成了“会话结束后 pending 卡住”的可靠复现条件。

## 解决方案

1. 在每次 checkpoint 返回 `failed` 时安排指数退避自动重试（初始 1 秒、上限 30 秒），不能仅记录日志后放弃。
2. 插件启动时扫描可处理的 active scopes，读取其 pending 数量和 `lastBufferedAt`。
3. 对已超过 `idleCheckpointMs` 的 scope 立即安排一次 `idle` checkpoint；未超时的 scope 仅设置剩余等待时间。
4. 复用现有 scope 锁和 in-flight 保护，避免启动恢复与正常事件重复提交同一 scope。
5. 增加启动恢复与失败重试回归测试，验证 pending 会在恢复/重试成功后清空。
