# DSH-WM-20261115-01：删除工作区记忆后同路径重建仍召回旧缓存

## 问题信息

- 发现日期：2026-11-15
- 发现会话：`session-3e96244a-9060-4504-82a6-aca1eea822af`
- 复现工作区：`C:\Users\QUAN\Downloads\测试`
- 相关模块或代码：`src/core.ts` 的 `WorkspaceMemoryStore.snapshotCache`、`archiveScope()`、`purgeArchivedScope()` 和 `readSnapshot()`
- 状态：已解决
- 验证情况：核心回归测试、设置页 API 运行时回归测试、构建后最小复现和完整自动化检查均已通过

## 问题描述

用户删除原“测试”工作区，并在记忆设置页永久删除其已归档记忆后，又以同一个文件夹路径创建了新的“测试”工作区。新 Session 第一轮询问是否存在工作区记忆时，插件仍向模型注入了旧工作区的“当前工作区仅用于测试玩法”等记忆。

磁盘删除实际成功：归档目录为空，新 scope 当前的 `memory_entries.json` 也是空数组。但运行中的 `WorkspaceMemoryStore` 仍保留删除前的 `snapshotCache`。新工作区沿用同一路径，因此计算出相同的 scope key，`readSnapshot()` 命中了旧缓存并把已删除条目交给召回流程。

### 可重复最小复现

在临时目录中执行以下等价流程：

1. 写入一条工作区记忆；
2. 调用 `readSnapshot()`，使旧快照进入缓存；
3. 调用 `archiveScope()` 和 `purgeArchivedScope()`；
4. 以相同 cwd 重新取得 scope 并调用 `readSnapshot()`。

实际结果：

```text
{"before":1,"archived":true,"purged":true,"after":1}
VERDICT=RED deleted scope leaked stale cached entries
```

磁盘 scope 已被归档并永久删除，但同路径读取仍返回 1 条旧缓存记忆，复现稳定且无需模型参与。

## 影响

- 用户永久删除工作区记忆后，只要 DSH 服务未重启，并以相同目录路径重建工作区，旧记忆仍可能被召回。
- 召回结果受当前查询相关性影响，因此可能只暴露一两条旧记忆，让用户误以为删除“部分成功”。
- 新一轮写入或服务重启会使现象消失或变化，导致问题不易稳定观察。
- 磁盘数据和设置页可能显示为空，但 Agent 实际仍能收到旧缓存，违反永久删除的用户预期。

## 原因判断

`readSnapshot()` 以 `${scope.key}:${scope.dir}` 为键缓存完整快照。正常写入会调用 `invalidateSnapshot()`，但：

- `archiveScope()` 只把活动 scope 目录移动到归档目录；
- `purgeArchivedScope()` 只递归删除归档目录；
- 两个方法都没有清除活动目录或归档目录对应的快照缓存。

scope key 又由规范化 cwd 确定。同一路径重建工作区后，新的 scope key 和活动目录都与旧工作区一致，因此直接复用了删除前的缓存。

## 解决方案

1. `archiveScope()` 在移动目录前后同时使活动 scope 和归档 scope 的快照缓存失效，避免并发读取重新写入旧缓存。
2. `purgeArchivedScope()` 在删除目录前后同时清理归档目录缓存和同 key 的活动目录缓存，覆盖同路径重建及并发读取场景。
3. 增加核心回归测试：先预热缓存，再归档、永久删除、同路径重建，断言 `readSnapshot()` 返回空条目和空摘要。
4. 增加设置页 API 运行时回归测试：预热活动与归档快照后永久删除，断言同路径 API 和运行时召回均不再返回旧条目。
5. 修复后重跑本问题的最小复现，并用真实交互顺序验证无需重启 DSH 也不会召回已删除记忆。
