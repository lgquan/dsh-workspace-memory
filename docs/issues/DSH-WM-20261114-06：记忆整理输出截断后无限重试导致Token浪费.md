# DSH-WM-20261114-06：记忆整理输出截断后无限重试导致 Token 浪费

## 问题信息

- 发现日期：2026-11-14
- 发现方式：用户提供 GitHub Issue 截图与 `call-audit.log`，并要求评估当前本地最新版
- 相关模块或代码：`src/index.ts`、`src/core.ts`、`test/runtime.spec.ts`
- 状态：已解决
- 验证情况：旧日志热重试审计为红；修复后的假 LLM 回归中，首次调用截断后只进行一次拆批恢复，等待超过旧版重试窗口仍保持 2 次调用，pending 保留且 scope 被暂停；48 项自动化测试、类型检查、构建、peer 检查及打包预检通过；当前 3080 实例已加载本地修复构建

## 问题描述

记忆整理请求把最多 40,000 字符的待整理对话和最多 12,000 字节的相关旧记忆交给模型，但输出上限固定为 1,500 tokens。模型输出被截断时，DSH 会返回 `finish.kind = "max-tokens"`；插件当前忽略该结束原因，随后以普通 JSON 解析错误处理截断内容。

失败批次会完整保留在 pending，并以 1、2、4、8、16、30 秒退避后无限重试。相同的输入和相同的 1,500-token 输出上限没有变化，因此确定性截断可能长期重放整批请求，持续消耗后台模型 token。插件也忽略流中的 `usage` 事件，设置页无法展示整理调用实际消耗。

“偷吃 token”是对不可见后台消耗的主观描述；现有证据能够确认的是缺少熔断、失败分类和用量可观测性，不能据此判断存在主观恶意。

## 证据与复现

### 用户提供的旧日志

- 第一次失败批次为 51 条消息、17 条已有记忆，错误为 `Unexpected end of JSON input`。
- 失败后到下一次调用的间隔依次包含 1.025、2.072、4.046、1.026、1.032、2.034、4.024、8.039 秒。
- 多次失败后 pending 保持 51 或 54，`added=0`、`updated=0`。
- 期间的新 `segment-end` 成功和进程重启会重置内存中的重试计数，重新从短间隔开始。
- 日志自身的 BOOT 版本字段为 `version=-`，无法只凭日志确认具体构建；但 `v0.2.16` tag 和当前源码均保留相同的 1,500-token 上限与无限重试逻辑。
- 旧日志没有记录 DSH 的 `finish reason` 和 `usage`，所以“这些 JSON 错误由 1,500-token 截断直接造成”是与错误形态和代码相符的强推断，而不是日志自身已经直接证明的事实。

使用只解析时间与 `CALL-START`/`CALL-FAIL` 的审计命令，得到：

```text
retry_gaps_seconds=1.025,2.072,4.046,1.026,1.032,2.034,4.024,8.039
hot_retries_under_60s=8
VERDICT=RED old-version hot retry reproduced
```

日志证明存在突发热重试和无限继续的条件，但不足以支持截图中“稳定每小时 300 次”的精确外推。无新事件且单次调用约 10 秒时，30 秒退避上限对应稳定态约每 40 秒一次；新 turn、成功的其他批次或服务重启可能重置退避并重新形成短间隔突发。

### 当前本地最新版复现

使用当前 `lib/index.js` 和假 LLM：每次返回截断 JSON、`usage={inputTokens:10000, outputTokens:1500}`，并以 `finish.kind=max-tokens` 结束。首次显式 checkpoint 后等待 1.2 秒，结果为：

```json
{"firstStatus":"failed","firstError":"Unterminated string in JSON at position 59 (line 1 column 60)","modelCallsAfter1200ms":2,"pendingAfterRetry":1}
```

这说明当前代码仍把明确的 `max-tokens` 当成普通 JSON 错误，并在 1 秒后重放相同 pending。现有自动化只覆盖“第一次失败、第二次成功”，没有覆盖永久无效输出、重试上限、熔断或重启后退避保持。

### 当前真实实例

当前 3080 端口实例的 4 个 scope 均为 `phase=idle`、`pending=0`、无最近错误。当前用户环境没有正在发生的重试风暴，但代码路径仍具备复现条件。

## 影响

- 确定性输出截断、无效 JSON、模型不兼容或错误配置可能触发无上限后台调用。
- 每次失败都会重新发送同一批输入；单批输入可包含最多 40,000 字符对话和 12,000 字节旧记忆，输入 token 浪费通常高于 1,500-token 输出本身。
- 退避计数只存在内存中，服务重启会丢失；普通 deferred turn 返回 `buffered` 时也会清空失败计数并改为 5 秒调度，活跃工作区可能反复回到短重试间隔。
- 固定记忆模型、关闭思考和全局并发 1 能降低竞争与推理 token，但不会阻止同一失败批次长期串行重试。
- 当前近实时策略在每个完整 turn 后 5 秒调度一次整理，这是用户选择的正常消耗；与失败重试浪费应分开统计和展示。
- 记忆摘要和相关召回还会给前台请求增加上下文，当前分别受 3,000 和 5,000 字节预算限制。这属于有界的功能性开销，不是本问题中的失控重试。

## 原因判断

1. 固定 `maxTokens: 1500` 与最大输入批次、潜在操作数量不匹配。
2. 流处理只识别 `finish.kind=error`，没有识别 `max-tokens`；也没有记录 `usage`。
3. JSON 解析失败、输出截断、网络错误、限流、配额耗尽和模型不可用共用同一种无限重试策略。
4. 重试没有最大次数、失败预算、熔断状态或人工恢复入口。
5. 重试元数据没有持久化，新 turn 和服务重启可重置退避。
6. 单次成功测试掩盖了永久失败场景，缺少“相同错误持续发生时必须停止自动调用”的回归门禁。

## 解决方案

1. 删除插件写死的 `maxTokens: 1500`，让所选模型和 provider 使用自身默认输出能力；模型正常停止时只按实际输出计费。
2. 收集并持久化每次整理的 `usage`，显式识别 `finish.kind=max-tokens`，不再等到 `JSON.parse` 才推断截断。
3. `max-tokens` 只进行一次有界拆批恢复，不递归继续拆分；恢复仍失败则保留 pending 并暂停该 scope。
4. JSON/契约错误只进行一次带严格格式提示的恢复调用；仍失败则暂停，不再定时重放。
5. 网络、限流和中止等瞬时错误按退避间隔重试，连续失败 5 次后暂停；配额、鉴权、模型不存在和其他确定性客户端错误立即暂停。
6. 把连续失败次数、最后错误及暂停状态写入 `state.json`。服务重启、新 turn 到达和新 Session 首次召回都不会绕过暂停状态。
7. 底层持久化累计调用数、失败调用数及实际输入/输出/总 token，用于诊断；普通设置页仅在工作区范围展示今日与累计总 token，并提供“立即重试”入口。修改记忆整理模型也会解除暂停并重新调度。
8. 保持固定记忆模型、最低推理档、5 秒合并窗口和全局并发 1，使记忆整理与前台对话模型配置隔离。
